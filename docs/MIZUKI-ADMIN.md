# 水月存档管理与满员开局

2026-11-08，1.2.0服务器修订。管理员使用普通浏览器登录 `/account`，打开「水月存档」。玩家客户端不能调用管理接口，普通用户无管理权限。

## 三项管理操作

| 操作 | 作用 | 保留内容 |
| --- | --- | --- |
| 关闭房间并保留存档 | 关闭指定水月房间，停止对应探索进程，全体成员返回大厅；已有检查点的探索转为挂起，旧进程租约失效 | 检查点与累计资料；尚无检查点则标记开局失败并释放占用 |
| 删除整次探索存档 | 删除指定探索的全队检查点、操作账本、历史结果、待发事件和账号占用，并关闭关联运行或恢复房间 | 每位成员已经累计到账的评分、细胞、投资及结局资料；不追缴历史奖励 |
| 重置玩家全部水月状态 | 删除指定玩家的全部相关探索及历史、关闭关联水月房间、清理游玩占用，并清空该玩家评分、细胞、投资与结局解锁 | 该账号身份、普通/排位及其他玩法；共享探索其他成员的累计资料 |

多人存档属于整次探索，不支持从共享检查点中直接挖掉某位成员。删除探索或重置参与者时会删除整局共享存档，解除所有相关成员的该局占用。确认页列出受影响玩家，必须填写管理原因并输入房间码、探索编号或账号名确认。账号已删除但仍有水月记录时，后台使用账号ID展示和确认。后台可搜索账号名、账号ID和最近100条探索，玩家重置会处理该玩家全部历史，不局限于最近100条。

## 权限与一致性

`GET /auth/admin/mizuki-control` 返回玩家状态、最近100条探索、实时水月房间和最近50条审计；可用 `accountId` 精确查询该玩家全部探索。`POST` 仅接受 `closeRoom`、`deleteRun`、`resetAccount`，要求管理员浏览器会话、同源JSON请求、受限请求体与非空原因。读取请求体后再次验证权限；房间实例标识、探索epoch、玩家探索集合用于拒绝过期确认。禁用、撤权及跨站请求不允许执行。

删除数据库内容及写入审计在单个事务内完成，失败回滚。事务提交到停止回调、杀死子进程和销毁房间之间没有异步让出；挂起先递增epoch。运行房间通过共享 `disposeRoom` 清除座位、观众、重连关联及对局内容引用，客户端收到明确管理员关闭提示。已删除探索的迟到写入因探索不存在被拒绝；队列中的请求由代理释放，不产生补发结算或重建存档。

审计记录保存在同一 `mizuki.sqlite` 的新增 `admin_audit` 表，包含操作者账号ID、操作、原因、目标及受影响账号。schema仍为1，新增表自动初始化；旧库在只读inspect中允许暂缺审计表，已有表则纳入摘要及SQLite备份验证。删除和重置不会删除审计。原账号库schema2、资源摘要、build49与应用签名保持。

## 满员开局

新探索和恢复探索均要求实际真人入座人数等于房间容量、所有成员连接在线、非房主成员准备完成；不满足时服务器在创建探索或claim旧存档之前拒绝请求，不启动子进程。客户端同步禁用开始/继续探索按钮，并显示当前人数和容量。单人游玩请将等待室左下角人数设为1；两人则设为2，依此类推。扩缩容规则仍见 [MIZUKI-ROOM.md](MIZUKI-ROOM.md)。

本规则修复此前不满员房间进入分队后无法确认的入口缺口；既有卡住探索可使用上述管理操作处理，不会自动清空真实玩家数据。手机仅横屏，保留旋转遮罩及长内容滚动。
